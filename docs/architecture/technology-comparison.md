# Technology Comparison — Phase 0

- **Reviewed:** 5 October 2026
- **Scope:** technology choices for a commercial map-first Nordic ski conditions product, initially ~10 resorts
- **Specification:** [`docs/product/master-context.md`](../product/master-context.md)
- **Decision record:** recommendations below are captured in the linked ADRs; implementation is deferred

## 1. Method and assumptions

This is a product-fit assessment, not a generic framework ranking or benchmark. “High/medium/low” and the comparative ratings are architectural judgments for this product; they are not vendor performance measurements. Public list prices and product limits can change and must be rechecked before purchase.

The product has both indexable pages and a persistent interactive map with coordinated filters, resort details and comparisons. It must collect third-party facts on a schedule, show source/freshness, support FI/EN/SV/NO SEO, and avoid unlicensed source access. The initial public product has no accounts, checkout, offline navigation or independent public API product.

**Operational assumption:** Phase 1 will prioritize official/authorized feeds and APIs. The chosen initial collector runtime is suitable for small network-I/O jobs; any source requiring a browser, heavy parsing or higher CPU/time limits reopens that decision before implementation.

## 2. Frontend and rendering framework

All three requested approaches can produce SEO-capable server-rendered pages and host an interactive map rendered by a library such as Leaflet or MapLibre. The deciding factor is not whether a framework can render HTML; it is whether the product is primarily a content site with one widget or an interactive application whose map, filters, comparison panel and future personalization share state.

| Criterion for this product        | Astro + Svelte islands                                                                                                                                                                                  | SvelteKit                                                                                                                                     | Next.js                                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Strongest fit                     | Content-first pages with isolated interactive islands                                                                                                                                                   | One interactive web application that also has public SEO pages                                                                                | Broad React application ecosystem; teams already invested in React                                                                                                 |
| SSR / static pages                | Excellent: static by default, selected routes can render on demand with an adapter.[5]                                                                                                                  | Excellent: SSR, CSR and prerendering are framework-level choices.[1][31]                                                                      | Excellent: App Router supports server/client rendering; Netlify documents current adapter support.[6][7]                                                           |
| Interactive map / shared UI state | Leaflet or MapLibre can be initialized in a Svelte island. If the map, filters, resort list and compare view share state, they tend to become one large island or require cross-island coordination.[4] | Natural fit: map, filters, list and comparison can be Svelte routes/components in the same application; initialize WebGL only in the browser. | Natural React components and extensive ecosystem; however, keep WebGL map widgets in client components and protect server/client boundaries.                       |
| SEO and i18n                      | Built-in localized routing and per-locale fallbacks; translated messages/content still need a content/i18n layer.[3]                                                                                    | SSR/prerender plus Paraglide JS provides typed messages and URL-based locale strategies for SvelteKit.[8]                                     | Strong SSR; routing and translation convention are assembled with an i18n integration such as next-intl rather than being a single App Router feature.[6]          |
| Maintainability                   | Simple static/content layer, but two component/routing contexts (Astro shell + Svelte island) can complicate shared app state.                                                                          | One framework/runtime for SSR, client interactivity, server endpoints and the later PWA; smallest conceptual split for this feature set.      | Mature conventions and broad packages; App Router's server/client components require disciplined boundaries.                                                       |
| Developer / AI-agent experience   | Static component patterns are approachable; agents must reason about Astro plus Svelte hydration directives and island boundaries.                                                                      | TypeScript/Vite, conventional load/server modules and a single UI model; smaller ecosystem than React/Next, so ADRs/tests matter.             | Highest general ecosystem familiarity and agent-generated examples; also the most React/Next-specific conventions to maintain.                                     |
| Cost / performance                | Often the least client JavaScript for content-only routes; not automatically cheaper if most app UI hydrates as Svelte islands.                                                                         | Small runtime choice does not set hosting cost by itself; per-route SSR/prerender permits performance tuning.                                 | Cost follows hosting/rendering, traffic and bundle choices rather than framework license; avoid making Vercel-specific features mandatory.                         |
| Lock-in / deploy                  | Adapter-based and portable; SSR islands need a server adapter.[5]                                                                                                                                       | Adapter-based; Netlify, Cloudflare and Vercel have SvelteKit adapters.[2][31][36][37]                                                         | Portable, but host-specific Next runtimes/features create more adapter considerations. Netlify currently documents an OpenNext adapter for major Next features.[7] |
| Map/background jobs               | Map widget is easy to isolate; Astro is not a reason to put collectors in the frontend host.                                                                                                            | Strong fit for map-driven product routes; scheduled collectors remain separate.                                                               | Strong fit, but framework API routes should not become an implicit scheduler or data-ingest architecture.                                                          |
| **Assessment**                    | Best if the product becomes editorial pages with a map widget.                                                                                                                                          | **Recommended:** best match for an interactive map-first application plus public SSR/SEO routes.                                              | Best if React/Next skills and ecosystem materially outweigh the additional framework conventions; viable fallback, not selected.                                   |

Astro’s content-first/islands design is attractive for low-JavaScript editorial sites, and its i18n routing is a real advantage.[3][4] In this product the map is a core surface rather than a small optional widget, so SvelteKit avoids an Astro shell plus a mostly-app-sized Svelte island. Next.js remains technically sound and strongest on broad ecosystem/agent familiarity, but that advantage is not enough to justify selecting it over the cleaner single-SvelteKit model for this app.

**Frontend decision:** SvelteKit + TypeScript, server-rendered public routes and selectively prerendered stable pages. Keep the map client-only; compare Leaflet for 2D simplicity with MapLibre for vector styling in a later UI spike.[40][42] Reopen the framework choice if the product shifts to predominantly editorial publishing or the development team explicitly prefers React/Next.

## 3. Database and spatial data

| Option                            | Cost / operations                                                                                                                                                                                  | Spatial fit                                                | Maintainability / portability                                                                                                                                   | Product fit                                                                                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Supabase PostgreSQL + PostGIS** | Managed; Free is useful for development but has inactivity pauses. Pro currently starts at $25/month and includes production-oriented backups/logs; additional projects are separately priced.[11] | PostGIS is available for points, polygons and linework.[9] | Standard Postgres and migrations are portable; Auth, Storage, Cron and Edge Functions add useful managed capabilities but are optional/vendor-specific.[11][34] | **Recommended:** spatial relational model plus a single early operations surface; choose explicit Stockholm region for Nordic data locality.[12] |
| Neon PostgreSQL + PostGIS         | Managed/serverless usage model; check compute, storage, branch and region costs at purchase.[27]                                                                                                   | Neon documents the PostGIS extension.[10]                  | Credible if the team wants database branching/serverless Postgres separated from auth, storage and jobs. This would mean assembling additional services.        | Genuine alternative; no decisive benefit for a ten-resort MVP that needs scheduled jobs, raw storage and future auth as well as a database.      |
| Self-managed PostgreSQL + PostGIS | Infrastructure line item can look lower; engineering/on-call, backups, upgrades, security and failure recovery become the team's responsibility.                                                   | Full extension control.                                    | Maximum control, but highest operations burden and less agent-safe without mature infrastructure automation.                                                    | Not justified before scale, residency or unit-economics requirements demand it.                                                                  |

**Decision:** Supabase Postgres/PostGIS as system of record; all schema changes live as reviewable migrations in Git and are applied through the CLI/workflow, not as dashboard-only edits.[34] Store normalized domain facts in relational tables; use object storage only for permitted raw snapshots and suitable map assets. The application remains portable at the SQL/schema level and does not make Supabase Auth or browser-side Data API a prerequisite for MVP.

## 4. Backend and API shape

| Shape                              | Advantages                                                                                                      | Costs / risks                                                                                                  | Decision                                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| SvelteKit server-only reads/writes | Single application boundary; secrets stay server-side; SSR can fetch current state without another network hop. | App server availability and DB access need monitoring; mobile/partners need a stable API later.                | **Use for the MVP web product**, plus SvelteKit server routes for browser map viewport data.                               |
| Direct browser → Supabase Data API | Fast client development and useful later for authenticated direct reads.                                        | Requires strict RLS on every exposed table, increases public attack surface and couples UI to database schema. | Do not use for privileged writes or MVP public data reads. Revisit for authenticated future features only after RLS tests. |
| Dedicated Node/Go API service      | Clear independent versioning, multi-client contract and separate scaling.                                       | Another deploy/runtime, credentials, observability and on-call surface before API consumers exist.             | Defer. Add when partner distribution, mobile-client needs or distinct scaling requirements justify it.                     |
| **Hybrid**                         | SSR/server-only now; later expose stable read-only API and narrowly permitted RLS access where beneficial.      | Requires contract discipline when public API is introduced.                                                    | **Recommended evolution path.** Model domain services independently from SvelteKit route handlers.                         |

The map can request a bounded read-only endpoint such as a viewport/resort-condition query. Public output is a product DTO, not a direct serialization of database tables. Version the API only when it becomes a contract for mobile, partners or other independently deployed clients.

## 5. Collectors and scheduling

These services are alternatives, not components that should all be launched at once. The first choice depends on permitted source formats and job duration; workload and licensing feasibility must be measured before implementation.

| Option                              | Job/runtime characteristics                                                                                                                                                                             | Cost / simplicity                                                                                                                                       | Observability / fit                                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Supabase Cron → Edge Function**   | Cron can run SQL or HTTP-invoke an Edge Function; Supabase recommends at most 8 concurrent jobs and 10 minutes/job. Edge Functions allow 2s CPU/request and a 150s free / 400s paid wall clock.[13][14] | Lowest integration count: schedule, function, database and run history are in Supabase.                                                                 | **Recommended for small, authorized, I/O-bound adapters.** Add an application `collector_runs` record and stale-source alert; do not assume the platform run log alone is a product audit trail. |
| Cloudflare Worker + Cron Trigger    | Scheduled workers use UTC triggers; plan/runtime limits differ, including CPU and invocation constraints.[17][18]                                                                                       | Workers Paid currently has a $5/month minimum and included usage; Free is lower cost but CPU-limited.[19] Adds another vendor next to Netlify/Supabase. | Good if collectors need independent deployment, Cloudflare queues/edge ecosystem, or more runtime headroom; writes to Supabase through an HTTP contract.                                         |
| Railway Cron                        | Standard container/Node runtime, job must exit; minimum five-minute spacing and execution is not guaranteed to the exact minute.[20]                                                                    | Usage-based plans/credits; straightforward Node dependencies, but separate runtime and secrets.[21]                                                     | Good fallback for a permitted adapter that needs Node packages, heavier parsing or longer work than Edge Functions allow.                                                                        |
| External scheduler — Upstash QStash | Publishes scheduled messages to an HTTP destination or queue; schedules use cron/UTC and initial activation can take up to 60 seconds.[38]                                                              | Free tier is 1,000 messages/day; usage plan lists $1 per 100,000 messages.[39] Adds a vendor, message accounting and destination authentication.        | Consider if durable cross-platform delivery/retry/dead-letter handling becomes a requirement; unnecessary for initial DB-owned jobs.                                                             |
| Netlify Scheduled Functions         | Scheduled-function execution has a fixed 30-second limit and scheduled runs are only for published deploys.[15][16]                                                                                     | Simple alongside the website; no extra scheduler vendor, but tied to the site’s deploy lifecycle.                                                       | Suitable for short housekeeping jobs, not selected for primary conditions ingestion where work may span several sources.                                                                         |
| Vercel Cron                         | Cron invokes deployed functions; available plan details and function duration/usage affect fit.[22][23]                                                                                                 | Convenient when hosting on Vercel; commercial plan/usage costs are separate from map/database.                                                          | Not selected because the recommended app is on Netlify and job ownership should not depend on changing the web host.                                                                             |
| GitHub Actions `schedule`           | Workflow schedules are supported, but GitHub notes schedule events can be delayed during high load.[24]                                                                                                 | Useful for CI, maintenance and scheduled reports; not a freshness-grade collector.                                                                      | Do not use for live snow/lift/weather ingestion.                                                                                                                                                 |

**Decision:** start with Supabase Cron + paid-project Edge Functions. Divide work by source group, stagger schedules, keep each invocation idempotent and short, record every run, and alert on freshness misses. If Phase 1 shows a licensed source needs more than the Edge CPU/wall-clock envelope, move only that adapter to Railway; Cloudflare Workers is the alternative if the team explicitly wants to operate collectors on Cloudflare.

No public resort page or score is allowed to imply real-time freshness the source does not provide. Store source observation time separately from collection time; use per-field staleness thresholds and show the `as of` time.

## 7. Hosting and deployment

| Host                     | Fit with SvelteKit                                                                              | Cost/performance/operations                                                                                                                                                  | Assessment                                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Netlify**              | Official SvelteKit adapter supports mixed prerender/SSR/client rendering and API routes.[2][31] | Public pricing currently lists Free and Personal at $9/month; credits/usage and plan terms need monitoring.[33] Deploy Previews are built for pull/merge-request review.[32] | **Recommended:** simplest fit with existing Netlify practices and review flow. Do not place the main ingestion schedule in Netlify.            |
| Cloudflare Pages/Workers | Official SvelteKit adapter can target Workers/Pages.[36]                                        | Strong CDN/edge and low entry pricing; edge runtime and usage limits need validation for application and collector needs.[18][19]                                            | Attractive consolidation option if Cloudflare becomes the chosen collector/queue/edge platform; adds migration from current Netlify practices. |
| Vercel                   | Official SvelteKit adapter exists.[37]                                                          | Current Pro list price is $20/month with usage credits; check compute and bandwidth details before committing.[23]                                                           | Strong framework preview workflow, but no product-fit gain enough to switch to Vercel for this SvelteKit app.                                  |

Netlify hosts the web app and provides PR previews; it is not a database, source registry or freshness scheduler. Static/global delivery is appropriate for content, while dynamic server paths should remain narrow and cache according to data freshness. Hosting and collectors deploy separately so a web release cannot silently change source cadence.

## 9. Localization and SEO approach

| Approach                          | Strength                                                                                                                 | Trade-off                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Astro built-in i18n routing       | Locale prefixes, default locale, browser preference and fallback routing are documented features.[3]                     | Translation message management, typed messages and coordinated map state are still application concerns. |
| **SvelteKit + Paraglide JS**      | Paraglide’s SvelteKit integration describes typed messages and SEO-friendly localized URLs, working with CSR/SSR/SSG.[8] | Needs a translation source/workflow and explicit checks for content-complete resort pages.               |
| Next.js + next-intl or equivalent | Next’s internationalization guide identifies next-intl and other integrations for App Router routing/translations.[6]    | Additional i18n library/configuration; no architectural benefit over SvelteKit for this product.         |

Use locale prefixes (`/fi/`, `/en/`, `/sv/`, `/no/`) from the first public route. Keep localized navigation and filters in message catalogs; resort copy/SEO content has explicit per-locale records. The English fallback is a presentation fallback only. Do not publish an untranslated resort page as a complete localized SEO page.

For each published page, generate stable localized URLs, self-canonical metadata and reciprocal `hreflang`; submit only canonical, content-complete routes in localized sitemaps. Google recommends annotating alternate localized versions and using the corresponding canonical URL strategy.[35] Locale-aware number/date/unit formatting uses standard internationalization APIs with the active locale and explicit product unit rules.

## 10. Cross-cutting evaluation and recommended stack

| Requirement                             | Decision / assessment                                                                                                                                                                                                                                       |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cost                                    | App/database baseline without tile delivery is about $34/month; optional MapTiler Flex raises it to about $64/month. A staging database adds $10; self-hosted tile infrastructure is not priced. These are planning figures, not all-in quotes.[11][27][33] |
| Performance / SEO                       | SvelteKit SSR for current condition summaries; prerender stable pages; cache dynamic output no longer than its freshness target; Leaflet or MapLibre only hydrates the map surface.[1][31]                                                                  |
| Maintainability / AI-agent friendliness | One TypeScript/Svelte app, adapter-per-source data contracts, score tests, ADRs, CI and preview-first review. Next.js has a larger AI/ecosystem footprint; SvelteKit reduces the app’s UI/runtime split. These are judgment calls, not benchmarks.          |
| Scalability                             | Ten resorts do not justify microservices. Postgres/PostGIS and a versioned product API can support expansion; increase worker/database capacity from measured load.                                                                                         |
| Vendor lock-in                          | Moderate platform use (Netlify/Supabase) but standard Postgres schema, provider-neutral adapters, exportable GeoJSON and replaceable map tile URL limit core lock-in.                                                                                       |
| Data collection                         | Supabase Cron/Edge for small I/O-bound jobs; measure run duration/failures. Railway/Cloudflare are tested fallback boundaries, not day-one dependencies.[13][14][20]                                                                                        |
| Observability                           | Persist application source-run/freshness state; use platform logs for diagnosis and alert on stale data. Supabase Pro currently lists seven-day log retention and Netlify Personal one-day observability; neither is a durable audit archive.[11][33]       |
| Future users/mobile/monetization        | Keep accounts/entitlements deferred; SvelteKit has a service-worker path for a future PWA, while mobile/API clients consume a stable server contract.[25]                                                                                                   |

### Recommended concrete stack

**SvelteKit + TypeScript + Paraglide JS → Netlify (SvelteKit adapter) → server-only domain/API layer → Supabase PostgreSQL/PostGIS in Stockholm → Supabase Cron + Edge Functions for authorized lightweight collectors → Supabase Storage for license-permitted raw snapshots → Leaflet or MapLibre renderer (deferred UI choice) → self-hosted OSM-derived or managed tile delivery (provider undecided) → GitHub Actions CI + Netlify PR previews + separate staging database.**

This stack is for the Phase 1 feasibility/design gate; it is not permission to start implementation. The first phase after architecture must resolve the ten resorts and license/data inventory. If any expected source cannot be used commercially or cannot meet the selected collector runtime, revise the relevant ADR before building the adapter.
