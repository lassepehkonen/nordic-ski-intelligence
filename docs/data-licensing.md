# Phase 1 — data licensing and reuse gates

- **Reviewed:** 5 October 2026
- **Scope:** FI/SE/NO ten-resort commercial product; public terms/docs checked at this date
- **Status:** legal screening, not legal advice. A lawyer or authorized data owner must confirm unclear cases before ingestion or publication.

## Rule for admission

A public URL, an API returning `200`, an open-data badge, or the fact that a competitor displays a value is not permission for this product to fetch, retain, transform, score, translate, cache, redistribute or monetize that value. Approve each **dataset + endpoint + fields + use** separately. Keep the source owner, exact terms/version and check date, rights basis, permitted operations, attribution, rate/cache/retention rules, expiry and approver in the rights record.

If a term is missing, contradictory or subject to a partner contract, default to **not approved**. Do not implement a scraper, store raw responses, publish derived scores, or place images/maps in the database until the relevant right is documented.

### Official resort sites: factual basics vs. feeds and protected material

Use each resort's official site as the primary factual source where its terms and technical constraints permit. The product may manually curate only necessary basic facts (for example, resort name, location, elevation/vertical profile and operator-published piste/lift totals), with a source URL and verification date. Treat each field and use as conditional until its applicable terms, robots directives, access method, commercial display, retention and attribution have been checked; do not infer permission from the page being public or the information being factual. Respect robots directives and technical restrictions; do not bypass blocks, reverse-engineer undocumented endpoints or bulk-scrape. This narrow curated-facts path is not approval for automated ingestion or for dynamic snow/lift/piste status, ticket prices, forecasts or webcam feeds. Do not copy editorial wording, photographs, videos, maps, graphics or substantial portions of a source database. When permission or a restriction is unclear, hold the field and link to the official source. See [official resort-source policy](official-resort-source-policy.md).

## Cache, request, and retention controls

- **MET Norway Locationforecast:** identify the application with a useful User-Agent and contact link; respect `Expires`; cache responses and use `If-Modified-Since`; do not repeat unchanged data, jitter scheduled requests and use no more than four decimal places for coordinates. No public fixed request ceiling or standard SLA was found.[1][3]
- **MET Norway Frost:** register an API client ID, obey response cache headers, retain the applicable per-response licence and quality code, and do not exceed average traffic of one request/second without contacting MET. No delivery guarantee is provided.[85][116][129]
- **FMI:** use the selected WFS product's update cadence and cache data. For snow depth, prefer the daily station observation; do not repeatedly poll the instant value. Published per-user limits are 20,000 Download/day, 10,000 View/day, and a combined 600 requests/5 minutes.[6][69] Road-weather observations are a separate Digitraffic product after FMI's August 2026 API change.[68]
- **SMHI:** query only documented/open services, retain/use response creation/update metadata, cache unchanged forecasts and daily snow-depth readings, and avoid excessive requests. Prefer CORE observation stations and preserve their quality/time metadata; no numeric public quota was found for the reviewed services.[127][128][131]
- **DMI:** filter to required variables/areas, cache when possible and align requests to the API's update cycle; fair-use monitoring may throttle misuse. No numeric public quota was found.[11][12]
- **Open-Meteo (deferred):** no API calls or subscription are planned now. If reintroduced for a documented coverage gap, use the paid commercial plan and obey its current limits, attribution and cache terms; the free endpoint is non-commercial.[13][14]
- **Mountain News / direct resorts:** no production cache duration can be inferred from public pages. Contract must define cache TTL, stale/fresh rules, raw-payload retention, test fixtures and derived/read-model use before the collector is written.[33][34][38]
- **LIPAS:** JYU's published CC BY 4.0 data terms allow commercial use; attribute Jyväskylän yliopisto/LIPAS and the snapshot date. No numeric quota/cache TTL is published; follow the production self-hosting guidance supplied by the user. The OpenAPI spec licence label is a separate unresolved documentation issue.[40][41][119]
- **OpenSkiData:** do not automate downloads more than once daily; weekly is enough for pilot geometry.[47]
- **OSMF tiles:** honor cache headers and the current tile usage policy; no tile scraping, prefetch, offline package generation or bulk download from the public endpoint.[45]
- **OpenSnowMap:** do not bulk download its hosted tiles; use an allowed data package and the matching licence instead.[48]
- **Tripadvisor:** default policy permits caching only Location IDs, not review content. No server cache, stored review database, HTML/JSON embedding or search indexing unless a contract expressly grants the exception.[56][58]
- **Google Places:** retain Place IDs only under the standard caching exception. When showing reviews/photos, follow author-credit and direct Google Maps source-link rules; confirm the EEA terms for the billing account.[52][53]

## Attribution implementation checklist

For every displayed/licensed value, preserve the source owner, exact dataset/endpoint, source-reported time, retrieval time, unit, transformation and the licence/contract revision. Render a linked attribution near the data or in an accessible source panel; identify normalizations/derived outputs without implying the source endorses the product.

At minimum, a weather credit must identify the relevant national service (FMI, SMHI or MET Norway), link the applicable licence and indicate normalization/changes. For station snow-depth values, show the station, observation time and quality context so the source is not misrepresented as the resort. LIPAS reuse must cite Jyväskylän yliopisto/LIPAS and the snapshot date; acknowledge data-contributing municipalities/providers where feasible.[119] OSM-based map data need visible linked `© OpenStreetMap contributors` credit. OpenSkiData needs its full multi-source credit, not only an OSM line. MapTiler's required map attribution must remain visible. Partner content uses the exact approved brand text/logo and review display placement.

## Approval record required before production

For every field/endpoint, attach: contract/licence and version; source owner/contact; exact pilot resort coverage; commercial use; fields and frequency; permitted normalization/scoring/localization; raw and derived retention; cache TTL and stale rules; rate limit; redistribution/SEO/mobile display permission; attributions; image/map/webcam rights; price and billing unit; termination/export plan; and legal/business approver. Recheck terms immediately before purchase and after material changes. Until approval is `approved`, no collector runs and no customer-facing data is populated from that source.
