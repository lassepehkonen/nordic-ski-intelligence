### Shared operator-source assessment

For all ten centres, official sources should lead on resort facts and, when an approved source is available, reported snow, operations, tickets and webcams. Manually curate only the minimum factual basics after checking applicable terms, robots directives and technical restrictions; preserve source URL and verification date. No reviewed resort page grants a general commercial feed for dynamic data. Public status pages may be linked while the product waits for permission, but scraping, bulk extraction and reverse-engineered endpoints are not fallbacks. Expected request counts above are budgeting assumptions, not a target schedule; use only the update cadence, cache headers and quotas in an eventual written/API agreement.

## Confidence and completeness notes

“Reliability” here is qualitative: operator-reported data are authoritative for the operator's own operations; national weather APIs are authoritative forecast providers; volunteer/registry geometry is suitable for discovery, not guaranteed complete; user reviews are subjective. No uptime or accuracy was independently benchmarked in this research. Every persisted observation must retain source, source time, fetch time, unit, parser version, and freshness state. Any missing permission, stale report or data disagreement is a visible limitation, never an implicit zero.

A nearest weather-station snow-depth value is **a station observation, not resort snow depth**. Select the nearest station that actually exposes the snow-depth parameter and has a recent, acceptable-quality reading; keep station identity, distance, elevation difference, observed time and quality metadata attached. The ten-resort station-coverage audit has not yet been done, so do not promise coverage until it is checked.
